# AI 생성 코드 리뷰 과부하 — 리서치 정리

## 1. 배경

AI 에이전트가 쏟아내는 코드량이 늘면서, "사람이 확인할 것만 추려서 보고하라"는 지시만으로는 리뷰 부담이 충분히 줄지 않는다는 문제가 제기됐다. 이 문서는 이 문제를 다룬 학술 논문과 업계 자료를 조사하고, 이 저장소(Dowin)의 하네스/스킬 구조에 적용할 수 있는 지점을 정리한다.

## 2. 문제의 본질: 큰 diff는 원래 사람 리뷰가 구조적으로 실패하는 영역

AI 이전부터 알려진 사실이지만, 이 문제의 근거로 다시 확인할 가치가 있다.

- **Cisco 사내 연구**: 200~400줄, 60~90분 리뷰에서 결함의 70~90%를 발견. 이 범위를 넘어가면 탐지율이 급락한다.
- **Google Modern Code Review 연구** ([sback.it, ICSE 2018 SEIP](https://sback.it/publications/icse2018seip.pdf), 리뷰 로그 900만 건 분석): 변경 크기가 커질수록 유의미한 코멘트 수는 줄고 리뷰 지연은 늘어난다. 건강한 리뷰 문화는 작고 단일 리뷰어가 보는 변경을 선호한다.

즉 "AI가 코드를 많이 써서 못 따라간다"는 새 현상이 아니라, 사람 리뷰가 원래 큰 배치에서 무너지는 구조적 한계를 AI가 규모로 노출시킨 것에 가깝다. 그래서 해법도 "더 열심히 본다"가 아니라 다음 세 방향으로 수렴한다.

1. 볼 필요가 없는 것을 걸러낸다 (리스크 기반 트리아지)
2. 볼 대상을 작게 쪼갠다 (변경 단위 축소)
3. 볼 곳을 정확히 짚어준다 (의도/드리프트 기반 리뷰)

## 3. 리스크 기반 자동 트리아지 — 가장 실전 검증된 방향

**Meta RADAR** — Automating Low-Risk Code Review at Meta ([arxiv 2605.30208](https://arxiv.org/abs/2605.30208), 2026)

- Diff Risk Score(DRS)로 diff를 채점 → 저위험은 LLM 리뷰 + 자동 랜딩, 고위험만 사람에게 라우팅
- 53만+ diff 처리, 33만+ 자동 랜딩, 하루 2.5만 건 규모 운영
- 핵심 결론: 자동 랜딩된 diff의 프로덕션 인시던트율이 비자동화 대비 **1/50**
- 시사점: 리스크 모델을 "경고용 정보"가 아니라 "게이팅 액션"으로 쓴 것이 핵심. 점수만 매기고 사람이 여전히 다 보게 하면 효과가 제한적이다.

**Governed AI-Assisted Engineering (GAIE)** ([arxiv 2606.22484](https://arxiv.org/html/2606.22484v1))

- 3단계 감독 모델: human-in-the-loop / human-over-the-loop / automated-with-monitoring
- 티어 결정 기준: 규제 영향, 고객 접점, **되돌리기 가능성(reversibility)**, 데이터 민감도

이 저장소가 이미 하고 있는 "사람이 확인할 것만 추려서 보고"는 이 흐름의 초기 버전이지만, 현재는 기준이 스킬별로 암묵적일 가능성이 크다. 위 연구들처럼 **명시적 채점 기준**(권한/인증 변경, 결제·데이터 처리, 외부 API 경계, 스키마/마이그레이션, 삭제 등 되돌리기 어려운 변경)을 정의해두면 트리아지가 세션마다 재현 가능해진다.

## 4. 리스크 채점의 근거 — 코드 처언(churn) 기반 결함 예측 연구

- **Nagappan & Ball** (고전 연구): 코드 처언(변경량·빈도)이 결함 밀도의 강한 예측 변수임을 보임
- **Just-in-Time Defect Prediction**: 커밋 단위로 결함 위험을 예측하는 후속 연구 계열
- 최근 연구(240만 커밋 분석): 파일 수명이 길고, 자주 편집되고, 변경이 넓게 흩어질수록 결함에 취약

실무 적용: "이 파일은 과거에 버그·롤백이 잦았다/자주 바뀐다" 같은 이력 신호로 **항상 사람이 확인할 파일 목록**을 유지하는 방식이 근거가 있다.

## 5. 리뷰 패러다임 자체를 바꾸는 최신 제안

**"From Code Review to Code Critique: Intent, Drift, and Spotlight for AI-Generated Diffs at Scale"** ([arxiv 2607.29516](https://arxiv.org/html/2607.29516v1))

- 질문을 "이 코드가 맞나?"에서 "에이전트가 내가 의도한 대로 했는가, **어디를 봐야 하는가**"로 전환
- self-review 워크플로우로 100만+ API 요청 처리, attestation-to-land 76%, 결함 0건 보고
- 주의: 이 수치는 저자 측 자체 보고이며 외부 재현 검증은 아직 확인되지 않음 — 참고용으로만 인용

**OpenAI "A Practical Approach to Verifying Code at Scale"** ([alignment.openai.com](https://alignment.openai.com/scaling-code-verification/), 2025.12)

- gpt-5-codex용 전용 리뷰 에이전트를 학습시켜 내부 PR 100%에 적용
- 80% 긍정 반응이지만, **개발자 과의존(over-reliance)**과 **검증 체크 게이밍** 같은 새 리스크도 동시에 보고
- 결론: 완전 자동화가 아니라 사람 감독이 계속 필요하다는 쪽 — 이 저장소의 "사람 확인 지점을 남겨둔다"는 방향과 일치

**서베이 논문 2건**

- "Quo Vadis, Code Review? Exploring the Future of Code Review" ([arxiv 2508.06879](https://arxiv.org/pdf/2508.06879))
- "3100 Opinions on Code Review in an AI World" ([arxiv 2607.07980](https://arxiv.org/pdf/2607.07980))
- 업계 흐름: 2025년 중반엔 에이전트 결과물을 거의 안 보고 머지하는 낙관이 있었지만, 2026년 초 들어 다시 사람 PR처럼 꼼꼼히 리뷰하는 쪽으로 회귀. 사람 감독이 강화되는 중인지 약화되는 중인지는 연구자들 사이에서도 아직 결론이 나지 않았다.

## 6. 이 저장소에 적용 가능한 지점 (제안 — 확정 아님)

아래는 리서치를 이 저장소의 기존 구조(harness-security-check, backend-quality-check 등 스킬, `docs/decisions/` 결정 로그)에 매핑해 본 것이다. **실행 여부와 우선순위는 사용자 판단이 필요하다.**

| 방향                                      | 근거                                   | 이 저장소 적용 지점                                                                                                                                                  |
| ----------------------------------------- | -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 명시적 리스크 채점 기준                   | Meta RADAR, GAIE                       | `harness-security-check` / `backend-security-check` 스킬에 "무조건 사람 확인" 트리거 목록(인증·권한, 결제, 외부 API 경계, 스키마 마이그레이션, 삭제류 변경)을 명문화 |
| 변경 이력 기반 위험 파일 목록             | Nagappan & Ball, JIT defect prediction | 과거 버그/롤백이 잦았던 파일을 표시해두고 해당 파일 변경 시 항상 리뷰 대상에 포함                                                                                    |
| 변경 단위 축소                            | Cisco, Google                          | 에이전트에게 한 번에 큰 diff 대신 200~400줄 단위로 커밋/PR을 나누도록 지시하는 컨벤션 추가                                                                           |
| 리뷰 질문 재구성 ("맞나"→"의도대로 됐나") | Code Critique 논문                     | 보고 형식에 "무엇을 의도했고 어디서 벗어날 수 있는지"를 명시하는 항목 추가 — 저비용으로 시도 가능                                                                    |

이 중 **투자 대비 효과가 가장 큰 것은 1번(명시적 리스크 채점 기준)**, **가장 저비용으로 바로 시도 가능한 것은 4번(리뷰 질문 재구성)**으로 판단된다. 3번(diff 쪼개기)은 근본적이지만 에이전트 워크플로우 변경이 필요해 상대적으로 도입 비용이 있다.

## 7. 확인이 필요한 지점 (사용자 판단 필요 — 임의로 결정하지 않음)

- 위 표의 방향 중 어느 것을 먼저 시도할지
- "무조건 사람 확인" 트리거 목록의 구체적 항목 (이 저장소의 도메인 특성에 맞게 조정 필요 — 예: Dowin의 결제/구독 로직, 팀 데이터 접근 범위 등)
- 200~400줄 기준을 이 저장소의 실제 PR 관행에 그대로 적용할지, 다른 기준을 쓸지
