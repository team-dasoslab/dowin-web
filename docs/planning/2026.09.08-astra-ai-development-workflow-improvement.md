# GPT-6 Astra 기반 AI 개발 워크플로우 개선안

## 1. 문서의 성격과 한계

이 문서는 사용자가 공유한 Eric Provencher의 “Rethinking skills and prompts for GPT-6 Astra” 해설을 평가 기준으로 삼아, 현재 Dowin 저장소의 AI 개발 운영 규칙을 검토한 결과다.

- 원문은 이 작업에서 별도로 조회·검증하지 않았다. 원문에 관한 서술은 사용자가 제공한 해설을 기준으로 한다.
- 현재 규칙에서 실제로 확인한 문제와, Astra에서 더 잘 작동할 가능성이 있는 미검증 개선 가설을 구분한다.
- 이 문서는 개선 방향과 적용 순서를 정의하지만, `AGENTS.md`, `codex.md`, Skills 본문을 즉시 변경하지는 않는다.
- 지시를 짧게 만드는 것이 목표가 아니다. 지식, 적용 조건, 승인 경계, 완료 조건을 서로 분리하는 것이 목표다.

## 3. 현재 워크플로우에서 확인한 문제

### 3.1. 실제 설정에서 확인된 문제

1. **규칙의 중복**
   - 시크릿 파일 금지, 원격 작업 승인, MCP 콘텐츠의 지시권 부인, 스킬 체인, 검증 명령이 `AGENTS.md`, `codex.md`, 개별 Skill에 반복된다.
2. **모든 비단순 작업에 같은 인테이크 비용 부과**
   - 작은 문서 개선이나 범위가 명확한 리팩터도 Linear 확인, 타당성 토론, Beads epic, 브랜치 생성을 먼저 수행한다.
3. **질문 트리거가 너무 넓음**
   - “유효한 방식이 두 개 이상”이면 그 차이가 결과·안전·사용자 경험을 유의미하게 바꾸는지와 무관하게 멈출 수 있다.
4. **검증의 점진적 확대와 일도양단 실패**
   - 스킬은 “가장 작은 유용한 검증부터”를 말하지만, 최종 게이트는 작은 변경에도 전체 domain suite를 요구하거나 E2E 선행 조건이 없으면 `pass`를 불허한다.
5. **스킬 설명과 본문의 트리거 불일치**
   - backend quality 설명은 API spec 단계 직후에도 쓰인다고 하지만 본문 Overview는 backend 구현 직후로 한정한다.
   - frontend quality 설명은 UI 또는 API connect 직후를 모두 포함하지만 본문 Overview는 API connect 직후로 한정한다.
6. **필수 체인과 실제 파일 구성의 불일치**
   - 모든 작업이 `dowin-release`로 끝나야 한다고 지시하지만 해당 Skill이 현재 저장소에 없다.
7. **README의 Skill 경로 드리프트**
   - `README.md`가 현재 없는 `.agents/skills/frontend/SKILL.md`, `quality-check/SKILL.md`, `security-check/SKILL.md` 등을 안내한다.
8. **세션 당 최소 4커밋 규칙과 사람 리뷰 규칙의 충돌 가능성**
   - 체인은 각 단계 직후 커밋을 요구하지만, 릴리스 외부에서는 각 커밋 전 사용자 리뷰와 승인을 요구한다. 구현을 연속 완료하라는 의뢰와 결합하면 단계별 중단이 발생한다.

### 3.2. 글의 문제의식을 적용한 미검증 가설

- 모든 정보 차이를 사용자 질문으로 돌리면 Astra의 합리적인 추론 능력을 활용하지 못하고 작업 중단이 늘어날 가능성이 있다.
- 모든 비단순 작업에 동일한 이슈·브랜치·PRD 체인을 적용하면 작은 개선의 시작 비용이 너무 커질 가능성이 있다.
- 개별 Skill이 매번 읽어야 할 문서를 나열하면, Astra가 필요한 파일을 스스로 탐색하는 능력과 중복되어 컨텍스트 비용이 늘어날 가능성이 있다.
- 최소 4커밋과 단계별 풀 게이트가 실제 버그 발견률을 높이는지, 리뷰 부담만 늘리는지는 현재 저장소 데이터로 실증되지 않았다.

## 4. 개선 원칙 5가지

### 4.1. 규칙을 “항상”이 아니라 트리거에 연결한다

AGENTS는 전체 지식을 담는 매뉴얼이 아니라 라우터와 절대 경계로 축소한다.

- 안전·보안·시크릿 규칙: 항상 로드
- 작업 분류와 Skill 선택 규칙: 항상 로드
- 도메인 지식: 해당 도메인을 변경할 때만 로드
- 배포·DB·WebView·결제 등 특수 지식: 해당 경계를 건드릴 때만 로드
- 커밋 컨벤션: 실제 커밋을 준비할 때만 로드

### 4.2. 질문은 “정보가 부족한가”가 아니라 “결과가 달라지는가”로 결정한다

Astra가 다음을 모두 만족할 때는 합리적인 가정을 밝히고 계속 진행하게 한다.

- 기존 코드·문서·관례에서 해답을 찾을 수 있다.
- 가정이 요청 범위를 확장하지 않는다.
- 로컬의 회복 가능한 변경이다.
- 사용자 경험, API 계약, 데이터 소유권, 비용, 보안 경계를 유의미하게 바꾸지 않는다.

다음은 계속 사용자 확인을 받는다.

- 복수의 유효한 선택지가 사용자 경험이나 공개 API 계약을 달라지게 하는 경우
- 데이터 삭제·마이그레이션·결제·권한·시크릿·원격 환경과 관련된 경우
- 요청한 범위를 넘어서 새 기능이나 구조를 추가해야 하는 경우
- 실패 시 자동 복구하기 어렵거나 외부 시스템에 영향을 주는 경우

### 4.3. 작업 크기와 위험도에 따라 체인을 다르게 적용한다

| 등급       | 예시                                                   | 트래킹/기획                         | 검증                                     | 사람 확인                                        |
| ---------- | ------------------------------------------------------ | ----------------------------------- | ---------------------------------------- | ------------------------------------------------ |
| T0: 단순   | 오타, 정확한 카피·스타일 수정                          | 인테이크·PRD 없음                   | 변경 파일 정적 확인                      | 최종 diff                                        |
| T1: 저위험 | 범위가 명확한 로컬 리팩터, 문서 개선                   | 간소 인테이크, task 단위 추적       | 관련 lint/type/test를 영향 기반으로 선택 | 최종 diff; 특별한 경계가 없으면 중간 정지 없음   |
| T2: 중위험 | 새 화면, 새 API, 도메인 규칙 변경                      | 정식 인테이크, 필요 시 PRD/contract | 도메인 품질 게이트                       | 계약·UX 결정점과 커밋 전 리뷰                    |
| T3: 고위험 | auth/권한, 결제, 스키마, 삭제, 배포, 시크릿, 원격 작업 | 정식 인테이크, 이슈·PRD·계약 필수   | 품질+성능/보안 게이트                    | 핵심 결정, 비가역 작업 직전, 커밋/원격 실행 승인 |

위험도는 변경 파일 수가 아니라 영향·회복 가능성·데이터 민감도로 판단한다.

### 4.4. 검증은 영향 기반으로 한 번 확장한다

1. 변경 중에는 가장 작은 관련 검증을 실행한다.
2. 실패가 이번 변경 때문이면 범위 안에서 수정하고 해당 검증을 다시 실행한다.
3. 최종에는 위험 등급과 변경 영향에 맞는 게이트를 한 번 실행한다.
4. 전체 suite는 광범위 공통 변경, 릴리스 준비, 영향 범위를 좁힐 수 없는 경우에만 쓴다.
5. 같은 커밋 후 다시 변경하지 않은 코드에 대해 동일한 전체 게이트를 단계별로 반복하지 않는다.

단, 로컬 검증이 정말 사용후 데이터를 쓰고 원격 환경에 접속하지 않는지 확인할 수 없다면 승인 생략을 기본값으로 삼지 않는다.

### 4.5. 의뢰에 완료 계약을 넣는다

작업 의뢰는 최소한 다음을 밝힌다.

```text
목표: 무엇을 바꾸는가
완료 조건: 어떤 동작·상태·검증을 통과해야 하는가
자율 범위: 로컬에서 어디까지 실행·수정·재검증해도 되는가
정지 경계: 어떤 선택·원격 작업·비가역 작업 앞에서 멈추는가
제외: 배포, 실제 메일·결제, 원격 DB 등 이번에 하지 않을 것
보고: 변경 의도, 핵심 diff, 검증 결과, 미해소 위험
```

“끝까지 해줘”보다 “로컬 관련 테스트 실행 → 이번 변경으로 생긴 실패 수정 → 영향 테스트 재실행 → 결과 보고, 배포와 원격 DB는 제외”처럼 종점을 적는다.

## 6. Skill 재설계안

### 6.1. 이름·설명은 전문성이 아니라 호출 조건을 설명한다

각 Skill 설명은 다음 세 문장 이내로 정리한다.

1. 이 Skill이 만드는 결과
2. 호출해야 하는 정확한 트리거
3. 호출하지 않아야 할 인접 작업(헷갈릴 때만)

예시:

```yaml
name: dowin-intake
description: >
  새 기능, 중·고위험 변경, 범위가 미확정인 요청의
  유효성·추적·작업 체인을 확정한다. 오타, 정확한 단일 수정,
  범위가 고정된 저위험 문서 작업에는 사용하지 않는다.
```

```yaml
name: dowin-frontend-quality-check
description: >
  사용자 동작·상태·i18n·모바일·회귀 위험이 바뀐 frontend UI 또는
  API 연동 단계 후에 검증한다. 카피·색상·간격만 바꾸는 저위험
  표현 변경은 영향 기반 검증으로 대체할 수 있다.
```

### 6.2. Skill 본문은 최소 라우터로 시작한다

Skill 본문의 첫 부분에는 다음만 둔다.

- 산출물과 완료 조건
- 필수 안전 경계
- 작업 유형을 참조 문서·스크립트에 매핑하는 표

세부 도메인 지식, 평가 체크리스트, 명령 예시는 `references/`와 `scripts/`로 분리한다. 단, 안전 규칙을 요약하다 누락하지 않는다.

### 6.3. 중복과 불일치를 자동 검사한다

하네스 변경 CI에 다음 정적 검사를 추가하는 방안을 검토한다.

- AGENTS에서 참조하는 Skill 경로가 실제로 존재하는지
- `.agents/skills` 원본과 `.claude/skills` 미러가 일치하는지
- Skill frontmatter 설명과 Overview/Next Step의 트리거가 일치하는지
- 동일 안전 문장이 여러 파일에서 서로 다르게 복제되지 않았는지
- 없는 문서·스크립트·Skill을 필수로 참조하지 않는지

## 7. 모델 혼용 전제

현재 저장소 규칙은 Codex, Claude Code, Antigravity 등 복수 하네스를 명시한다. 또한 현재 세션에서는 Astra, Sol, Luna 모델 선택지가 존재하지만, 팀이 실제로 어떤 모델을 어떤 작업에 쓰는지는 확인하지 못했다.

따라서 다음을 기본으로 한다.

- 저장소 공통 규칙을 Astra 전용으로 가정하지 않는다.
- 시크릿, 원격 승인, 프롬프트 인젝션, 타입 우회 금지는 모델과 무관하게 공통으로 유지한다.
- 자율성에 관한 차이는 안전 규칙을 복제하지 말고, 의뢰의 `자율 범위`와 위험 등급으로 표현한다.
- Sol/Luna에 필요한 추가 안내가 실증되면 공통 규칙을 다시 늘리기보다 모델/역할별 프로파일이나 의뢰 템플릿에 둔다.

## 8. 적용 순서

### 8.1. 1단계: 드리프트와 충돌부터 수정

거의 판단이 필요 없고 모델과 무관하게 잘못된 부분이다.

1. `dowin-release` Skill의 실제 존재 여부를 확정하고 참조를 복원하거나 제거한다.
2. README의 오래된 Skill 경로를 현재 카탈로그와 맞춘다.
3. backend/frontend quality Skill의 frontmatter와 Overview 트리거를 일치시킨다.
4. `codex.md`의 잘못된 `pnpm@4.10.0` 표현을 `package.json`/README의 현재 버전과 대조한다. README는 `pnpm 10.33.2`를 명시하므로 현재 두 문서가 충돌한다.

### 8.2. 2단계: 중복을 하나의 권위 위치로 합침

1. 안전 경계의 권위 원문을 `AGENTS.md`로 고정한다.
2. `codex.md`는 Codex에만 필요한 차이와 의뢰 예시에 집중한다.
3. Skill은 공통 규칙을 복제하지 않고, 트리거와 도메인 추가 제약만 제공한다.

### 8.3. 3단계: 위험 기반 인테이크·질문·검증 도입

1. T0~T3 분류를 스킬 트리거와 체크리스트에 반영한다.
2. `No Silent Gap-Filling`을 `No Silent Material Decisions`로 정교화한다.
3. 품질 게이트를 영향 기반 검증과 최종 전체 게이트로 분리한다.
4. 커밋 개수는 고정하지 않고, 실제 수행한 stage와 intent에 따라 나눈다.

### 8.4. 4단계: 지표로 검증한다

변경 전 2~4주, 변경 후 2~4주의 표본을 비교한다.

- 작업당 사용자 확인 횟수
- 첫 요청에서 최종 diff까지 걸린 시간
- 확인 후 “그대로 진행” 응답으로 끝난 무정보 질문 비율
- 변경 당 검증 실행 횟수와 소요 시간
- CI 실패율, 리뷰 반려율, 머지 후 결함·롤백
- 사용자가 직접 수정한 하네스 규칙 횟수

속도가 느낌상 빨라졌다는 것만으로 성공을 판정하지 않는다. 중단이 줄어도 결함·롤백이 늘면 실패다.

## 9. PRD

### 9.1. 배경 및 문제 정의

현재 Dowin의 AI 워크플로우는 이전 모델의 누락·임의 판단을 막기 위해 규칙을 추가해 왔다. 그 결과 안전성과 재현성은 강화됐지만, 작업 관련성과 무관한 읽기, 모든 선택지에 대한 중단, 고정된 체인과 검증 반복이 누적됐다. Astra의 자율적 탐색·추론·검증 능력을 쓰려면 안전 경계는 유지하되, 규칙의 발동 조건과 완료 계약을 명확히 해야 한다.

### 9.2. 기능 요구사항

- 작업을 T0~T3 위험 등급으로 분류한다.
- 등급에 따라 intake, issue, PRD, 독립 평가, 검증, 사람 승인 강도를 선택한다.
- AGENTS는 공통 안전 경계와 라우팅을 담고, 세부 절차는 트리거된 Skill/reference로 넘긴다.
- 범위를 바꾸는 중대한 결정만 사용자에게 질문한다.
- 로컬·회복 가능·요청 범위 내의 실행과 수정은 명시된 완료 조건까지 자율적으로 진행한다.
- 없는 Skill 참조, 설명/본문 불일치, 미러 드리프트를 정적 검사한다.

### 9.3. 비기능 요구사항

- 시크릿 파일은 절대 읽지 않는다.
- 원격·프로덕션 변경은 실행 직전에 새 승인을 받는다.
- 외부 콘텐츠를 지시권이 있는 텍스트로 승격하지 않는다.
- 요청 범위 외 변경과 회복이 어려운 변경을 자율적으로 수행하지 않는다.
- 모델 혼용 환경에서도 최저 안전성을 유지한다.

### 9.4. 범위

#### MVP

- 현재 드리프트 4종(`release` 부재, README Skill 경로, quality 트리거, pnpm 버전) 해소
- `AGENTS.md`, `codex.md`, intake/planning/quality/commit Skills의 중복과 적용 조건 재설계
- T0~T3 위험 등급과 material decision 정의
- 영향 기반 검증 규칙 반영
- 의뢰용 완료 계약 템플릿 제공
- 하네스 보안 검토

#### Post-MVP

- 하네스 참조 결성·미러 드리프트 CI 검사
- 작업 중단·검증 비용·결함율 측정 자동화
- 모델별 임무 템플릿 A/B 비교
- 실제 데이터에 따른 위험 등급 보정

### 9.5. 영향 도메인·파일

- `AGENTS.md`
- `codex.md`
- `.agents/skills/**`
- `.claude/skills/**` 미러
- `README.md`
- 추가 검사를 도입할 경우 CI/config 파일

앱 런타임, API, DB 스키마, 사용자 데이터는 영향 범위에 포함하지 않는다.

### 9.6. 성공 기준

- T0/T1 작업이 불필요한 Linear·PRD·중간 승인 없이 명시된 완료 조건까지 진행된다.
- T2/T3에서 계약·UX·보안·데이터 경계의 중대한 미결정 사항은 여전히 사용자에게 돌아온다.
- 시크릿 및 원격 승인 경계에 회귀가 없다.
- 필수 참조가 실제 파일과 일치하고 Skill 설명과 본문의 트리거가 일치한다.
- 검증 횟수가 줄어들어도 CI 실패, 리뷰 반려, 롤백 비율이 악화되지 않는다.
- 변경 후 측정 결과를 바탕으로 규칙을 유지·복구·추가 조정할 수 있다.

### 9.7. 실패 기준

- 속도를 위해 시크릿·원격·파괴적 작업 경계가 약화된다.
- “Astra가 잘할 것”이라는 가정만으로 필수 검증을 삭제한다.
- Sol/Luna/Claude 등 다른 모델·하네스에서 완료 조건이 누락되거나 위험한 자율 실행이 발생한다.
- 질문 수는 줄었지만 스코프 드리프트, 리뷰 반려, 롤백이 증가한다.
- 규칙이 여전히 여러 권위 파일에 복제되어 서로 다르게 노후화된다.

### 9.8. 오픈 이슈

- `dowin-release` Skill은 삭제된 것인가, 아직 복원되지 않은 것인가?
- T0/T1 작업도 Linear 또는 Beads로 반드시 추적해야 하는가?
- 커밋 전 사람 리뷰를 작업 끝에 한 번으로 묶을 수 있는 위험 등급은 어디까지인가?
- 로컬 테스트가 실제 원격 서비스·공유 데이터에 접속하지 않는다는 것을 어떤 config/CI 검사로 보장할 것인가?
- 팀원이 실제로 쓰는 모델·하네스 조합은 무엇인가?

### 9.9. 다음 단계 Action Items

1. 팀이 오픈 이슈와 T0~T3 경계를 검토한다.
2. `dowin-harness-security-check`로 개선안이 시크릿·원격 승인·지시권 경계를 유지하는지 확인한다.
3. 1단계 드리프트 수정을 별도 intent로 구현한다.
4. `AGENTS.md` 라우터 축소와 Skill 트리거 재설계를 작은 diff로 나누어 구현한다.
5. `.claude/skills` 미러를 동기화하고, 하네스 보안 검토와 참조 무결성 검사를 실행한다.
6. 2~4주 후 중단·검증·결함 지표로 규칙을 재평가한다.

## 10. 우선 검토 순위

1. **필수 참조 드리프트 해소**: 없는 `release` Skill과 README 경로는 모델 성능이 아니라 실제 워크플로우 결함이다.
2. **중대한 결정만 질문하도록 정의**: Astra의 자율성을 활용하면서 사용자 의도를 지키는 핵심 변경이다.
3. **위험 기반 intake·검증**: 저위험 작업의 중단과 반복 검증을 줄이되 T2/T3의 보호는 유지한다.
4. **권위 원문 단일화**: AGENTS에 안전 규칙을 남기고 나머지는 참조하여 드리프트를 줄인다.
5. **측정 후 조정**: 질문·테스트 횟수만이 아니라 결함·롤백을 함께 봐야 한다.
