# 의사결정 로그 (Decision Log)

`docs/planning/2026.07.13-ai-engineering-application-plan.md` §9.2 갭 3 대응: "AI가 A안을 제안했는데 사람이 B로 결정했고 이유는 C였다"를 남기는 로그가 없다는 문제를 최소 비용으로 메운다.

## 언제 쓰나

**매 결정마다 쓰지 않는다.** 아래 둘 중 하나에 해당할 때만 기록한다.

- 되돌리기 어려운 결정 (브랜치/파일 구조, 데이터 스키마 방향, 되돌리는 데 비용이 큰 선택)
- 다음 세션(사람이든 AI든)이 같은 지점에서 다시 헷갈릴 가능성이 높은 결정 (여러 유효한 선택지가 있었고, 왜 이걸 골랐는지가 코드/문서만 봐서는 안 드러나는 경우)

일반적인 구현 디테일, 되돌리기 쉬운 선택, 이미 컨벤션 문서에 답이 있는 것은 여기 남기지 않는다 — 이 로그 자체가 소음이 되면 아무도 안 읽는다.

## 형식

`docs/decisions/YYYY.MM.DD-slug.md` 파일 하나에 아래 4개만 짧게:

```markdown
---
작성일시: YYYY-MM-DD HH:MM:SS
문서유형: reference
상태: active
---

# <결정 제목>

**상황:** 왜 이 결정이 필요했는지 1~2문장.

**옵션:** 검토한 선택지들 (있었다면 AI가 제안한 안 포함).

**결정:** 무엇을 골랐는지.

**이유:** 왜 이걸 골랐는지 — 다음에 같은 지점에 서는 사람/AI가 "왜 저렇게 안 했지?"라고 묻지 않을 정도로.
```

3~5문단이면 충분하다. 예시는 `2026.08.14-ch9-doc-branch-reconciliation.md` 참고.

## 사용 규칙

- 매 결정마다 새 파일을 만들지 않는다 — 위 기준에 해당할 때만.
- ADR(Architecture Decision Record)처럼 무겁게 번호를 매기거나 상태 전이(proposed/accepted/superseded)를 관리하지 않는다. 이 저장소 규모에서는 오버스펙이다.
- 오래돼서 더 이상 유효하지 않은 결정이면 상태를 `superseded`로 바꾸고 대체 문서를 링크한다 — 삭제하지 않는다 (그 결정이 왜 바뀌었는지도 근거가 된다).
